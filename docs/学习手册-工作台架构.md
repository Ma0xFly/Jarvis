## 1. 一句话，和一张图

**你写一张卡，机器把它干完，你签字，经验留下来。**

```
你 ──写卡──► 白板 ──调度室──► 工人 ──干活──► 质检台 ──你签字──► 档案
     (待办)   (kanban)  (dispatcher)  (worker)   (review)   (done)   (固化)
```

这张图里只有"你"和"档案"是人类时间，中间三站都是机器时间。**整个项目的全部价值，就压在"档案"那一格上**——如果每张卡干完什么都没留下，那这套系统只是一个更花哨的待办清单。

## 2. 五个零件，用一间工厂讲完

### 2.1 白板：`kanban.db`

**它是什么**：一个 SQLite 文件，`~/.hermes/kanban.db`（当前 364 KB）。所有任务、评论、状态、运行记录都在这一个文件里。

**解决什么问题**：如果"任务进行到哪一步"这件事同时存在于网页、聊天记录、你的记忆里，三份一定会对不上。所以规定：**只有一个地方算数**。

**类比**：车间墙上那块白板。调度员、工人、质检员都看同一块板，谁改了都写在上面。你在办公室用手机看监控，看到的也是这块板。

**优点**：永不漂移；备份就是复制一个文件；任何程序都能读。
**缺点**：单机。它是个文件，不是服务，两台电脑不能同时写。所以"把工作台挂到云服务器"这条路默认走不通——不是不想做，是这块板的物理形态决定的。

**真实例子**：CLI、网页、AI 工人三方看到的永远是同一份状态，因为它们读的是同一个文件，不是三份拷贝。

---

### 2.2 调度室：Hermes 的 gateway

**它是什么**：一个常驻进程（`hermes gateway`），里面装着两样东西——**会话服务**（AI 在哪说话）和**调度器**（`dispatcher`，每 60 秒扫一次白板）。

**解决什么问题**：总得有人决定"这张卡现在该谁干"，而且不能靠你手动点。调度器就是那个每 60 秒巡一次车间的人。

**类比**：工厂的调度室。它不看你的微信，只盯着白板：**凡是写着"就绪"的卡，谁空谁领走**。

**它具体做的事**（顺序很重要）：

1. 每 60 秒扫一遍 `ready` 状态的卡，按优先级、创建时间排序
2. 挑一张，**原子地**打上"我领了"的标记（防止两个工人抢同一张）
3. 启动一个子进程，让对应工种的工人接手
4. 工人干完或卡住，把状态写回白板

**优点**：你不需要在场；重试、并发、失败恢复都是它的事。
**缺点**：你不在场，所以**它干错了你也不知道**——这正是"验收"这一站存在的理由。

---

### 2.3 工人：三个 profile

**它是什么**：profile 是**一套工牌**，不是一个人。`~/.hermes/profiles/` 下现在有四个：

| 工牌 | 干什么 | 模型 |
|---|---|---|
| `researcher` | 查资料、调研、出报告 | `group/group`（便宜的杂活组） |
| `housekeeper` | 巡检、整理目录、做表格 | `group/group` |
| `coder` | 写代码，重的活转包给 dsh | `group/main`（强模型） |
| `skeptic` | 专门挑毛病（平时不用） |  |

**一个 profile 里装三样东西**，这是最容易忽略的一点：

1. **模型 pin** —— 这个工人用哪个模型
2. **skills** —— 它的操作手册（`~/.hermes/profiles/<名字>/skills/`）
3. **SOUL.md + 记忆** —— 它是谁、它记得什么

**解决什么问题**：如果所有活都给一个"全能 AI"，它既会用最贵的模型干最便宜的活，也会把写代码的习惯带到写周报里。分工人 = 分工具、分手册、分预算。

**优点**：成本可控、行为可预期、一个工人改坏了不影响别的。
**缺点**：多一份维护。三个 profile 就是三份 SOUL、三份 skill 清单——所以**别轻易加第四个**，加之前先问"它和现有的差在哪"。

---

### 2.4 总机：magpie（`127.0.0.1:3425`）

**它是什么**：一个本地网关。所有 worker 调模型都不直连厂商，而是先打到它。

**解决什么问题**：
- 你手上有 OpenRouter、Gemini、MiniMax、硅基流动等十几家账号，**额度会突然用完、会限流、会宕机**
- 每家的 API 格式、密钥、计费都不一样

magpie 让你只对一组"名字"编程：`group/group` = 一堆便宜模型的轮转组，`group/main` = 强模型组。**某一家挂了，它在 100 毫秒内换下一家，你的代码不用改。**

**类比**：工厂的总机。你拨"杂活组"，总机自己决定接给谁；某条线占线，它自动转接。

**优点**：一家挂了不影响你；成本能统一看（`~/.config/magpie/usage.jsonl`）；还能做敏感信息脱敏。
**缺点**：多一跳，多一个可能出故障的地方。**排查时永远要问一句：是模型的问题，还是总机的问题？**（§7 有对应的探针）

---

### 2.5 外包长工：dsh

**它是什么**：另一个 AI 编程工具（类似 Claude Code 那一类），命令行调用，`dsh --profile headless --json "任务"`。

**解决什么问题**：写代码这类活，需要**长时间连续改十几个文件**。Hermes 的 worker 适合"一次干一件事、干完汇报"，不适合连续几小时的重构。所以 `coder` 这个工人领到重活时，会把它转包给 dsh，dsh 干完再回写结果。

**类比**：厂里的正式工（coder）接到一个大件，自己不上，打电话叫外包队（dsh）来做。做完货交给正式工，正式工再登记入库。

**优点**：重活有专门的工具；dsh 的上下文管理比通用 agent 强。
**缺点**：**多了一层嵌套，记录容易断**。一张卡 → 一个 Hermes 会话 → 一个 dsh 会话，中间任何一环没记 session id，你就再也找不回当时的现场。这是已知的三处断链之一（§7 会讲怎么判断）。

## 3. 一次任务的完整生命周期

跟着一张卡走一遍，这是理解整个系统最快的方式。

### 第 1 站：想法 → 卡（`triage`）

你说一句"调研 Tailscale 和 ZeroTier"，系统把它变成一张卡，状态是 `triage`（待整理），同时打上 `bucket=today`（今天的事）或 `bucket=long`（以后的事）。

**这一站只有一件重要的事**：卡上有两栏——**输入**（用哪些材料）和**验收**（怎样算对）。验收那栏空着，这张卡就永远派不出去。

> 为什么？因为"怎样算对"只有你知道。机器可以替你干活，不能替你判断。

### 第 2 站：拖进流水线（`ready`）

你把卡从仓库拖进流水线。这个动作有两个含义：

1. **状态从 `triage` 变成 `ready`** —— 告诉调度室"这张可以派了"
2. **预算和禁区被快照下来** —— 三层默认（全局 → 规则 → 卡）算出一个最终值，写进这张卡的元数据

**为什么要快照**：三个月后你改了全局预算，回头查这张卡"当时按什么规则跑的"，如果读的是"当前默认"，你永远查不清。**记录必须是当时的，不是现在的。**

### 第 3 站：调度室认领（`running`）

60 秒内，调度器扫到它，打上认领标记，拉起 `researcher`。状态变 `running`。

**注意**：`running` 是**机器专属**状态。你手动改不了，也不该改。这是设计上的保护——状态机里有些格子是只读的，否则"谁在干什么"就没人说得清了。

### 第 4 站：工人干活

`researcher` 在一个**独立会话**里干活（`source=kanban`、`platform=cli`）。它会：
- 读这张卡的正文和最近 30 条评论
- 调工具（搜索、浏览器、读文件）
- 超过预算就自己停

**这一站你看不见**，但每一步都有记录：`~/.hermes/hermes-agent/state.db` 里有完整对话，`kanban/logs/<task>.log` 里有工具调用流水。

### 第 5 站：交活 → `review`（不是 done）

干完，卡进 `review`（待验收）。

> **这里有个容易踩的坑**：AI 工人默认的收尾动作叫 `kanban_complete`，它会直接把卡标成 `done`——**跳过你**。我们这套流程要求工人用 `request_review` 收尾，卡才停在 `review` 等你。这一条必须写进每个 worker 的 skill，否则整个验收环节形同虚设。

### 第 6 站：你签字（全屏验收）

点右上角「待你处理」，一张一屏：左边产出物，右边你当初写的验收标准 + AI 的自述（交付了什么、依据什么、哪里没底）。三个键：

- `A` 收 → 进 `done`
- `R` 不收 → **必须写一句为什么**，卡退回仓库
- `S` 跳过 → 排到队尾

**为什么"不收"必须写理由**：那句理由是这套系统里唯一会自动变成规则的东西。没有它，你每次都在用同样的方式退回同一类错误，系统永远学不会。

### 第 7 站：留下经验（固化）

卡进 `done` 之前，还要登记一件"下次能直接用"的东西——一条规则、一次操作手册修订、或一个能重跑的脚本。

然后这套流程才会产生复利：**第一次 40 分钟，第二次 8 分钟，第三次机器自己跑。**

## 4. 六个必须懂的概念（白话版）

### 4.1 状态机：为什么不能随手改状态

**类比**：电梯。你不能从 3 楼直接跳到 1 楼而不经过 2 楼——不是不能，是那样电梯会以为自己在哪一层都不知道了。

一张卡的状态只能沿着固定路线走，因为**每个状态都对应一套"谁可以动它"的规则**：

- `running`：只有调度器能设，因为它代表"有个进程正在跑"，你手动设了但没有进程，就永远卡在那
- `blocked → ready`：必须走"解封"这条专门的路，它会顺带迁移原因、补事件；直接写状态会绕过这些，事后查不到这张卡为什么被卡过
- 仓库里的卡统一是 `triage`，不分"今天/长期"——那两个是**标签**（`metadata.bucket`），不是状态

**这是整个系统最反直觉的地方**：看起来"改个字段"的事，其实是在改"谁负责"。

### 4.2 profile：工牌，不是人

一个 profile = 模型 + 手册 + 记忆。所以"给 researcher 加一个技能"和"给 researcher 换模型"是同一类操作：你在改这个工人的配置，不是在改某个 AI 的天赋。

**实用推论**：新活先问"现有三个工人谁能干"，别急着开新 profile。开一个就要维护一套手册。

### 4.3 skill：操作手册

`skill` 就是一份 Markdown 写的操作手册，AI 在需要时会读它。它和"提示词"的区别是：**提示词是一次性的，skill 是长期的、有版本的、会被反复读的。**

所以踩过的坑要写进 skill，而不是写进聊天记录。聊天记录会滚走，skill 不会。

### 4.4 REST / fetchJSON：对讲机

网页和后台之间不说话，只递纸条（HTTP 请求）。`GET /tasks/xxx` 是"把这张卡给我看看"，`PATCH /tasks/xxx` 是"把这张卡改成这样"。

**关键细节**：插件里不能直接用浏览器的 `fetch`，要用宿主给的 `SDK.fetchJSON`——因为 dashboard 有认证令牌，插件自己发请求会被挡。这是"借宿主的对讲机"。

### 4.5 轮询 vs 推送：为什么是 5 秒

网页不知道后台发生了什么，两种办法知道：
- **推送**（WebSocket）：后台主动告诉你，实时，但要维持一条长连接，断线重连逻辑很麻烦
- **轮询**：每 5 秒问一次"有变化吗"，简单，代价是最多晚 5 秒

选轮询是因为：这是单人本机工具，晚 5 秒没人在意；而长连接的故障模式（断线、重连、消息重复）会吃掉你两天。

### 4.6 为什么插件不能自带 React

React 是一个"记住界面状态"的库，它靠**全局单例**工作。如果一个页面里装了两份 React，两份各自记各自的状态，hooks 就会报错——而且报的错通常和真正的原因完全无关。

Hermes 的 dashboard 已经把 React 放进页面了（`window.__HERMES_PLUGIN_SDK__.React`），所以插件的产物**必须把 React 当外部依赖**，不能打包进去。独立版没有这个宿主，所以要自己打包一份。

**同一份源码，两种打包**——这就是我们选 Vite 双 build 的全部原因。

## 5. 代码地图：改哪里会怎样

| 路径 | 它是谁 | 改了会影响 | 能不能改 |
|---|---|---|---|
| `workbench-ui/src/` | 前端唯一源码（React+TS） | 插件版 + 独立版同时变 | ✅ 只改这里 |
| `workbench-app/server.py` | 独立版的壳（99 行） | 只影响 8787 | ✅ 可加 `/api/workbench/*` |
| `workbench-app/web/` | 独立版**产物** | 下次构建被覆盖 | ❌ 别手改 |
| `~/.hermes/plugins/workbench/dashboard/` | 插件**产物** | 下次构建被覆盖 | ❌ 别手改 |
| `~/.hermes/hermes-agent/` | 上游 Hermes | 升级会覆盖，且失去可升级性 | ❌ 全线禁止 |
| `~/.hermes/kanban.db` | 白板 | 所有状态 | ❌ 禁止直接写 SQL |
| `_bmad-output/specs/.../SPEC.md` | 契约 | 所有下游 story | ✅ 改设计先改它 |
| `routing.json`（待建） | 分派规则 | 派活给谁 | ✅ 改完即生效 |

**三种典型改动，走哪条路**：

- **改样式/文案/布局** → `workbench-ui/src/styles/*` 和组件 → `npm run build` → 刷新
- **加一个新接口**（比如"派发"） → `workbench-app/server.py` 加 `/api/workbench/xxx` → 前端 `src/api/` 调它。**不要**去改上游 `plugin_api.py`
- **加一个工种** → 建 profile（模型 + SOUL + skills）+ 在 `routing.json` 里加一条规则 + 在界面加个类型选项。三处都要动

## 6. 五个探针：自己验证，不靠感觉

```bash
# ① 服务活着吗（三个端口都在听）
ss -ltn | grep -E "9119|8787|3425"
# 期望：三行，全部 127.0.0.1

# ② 工作台后端正常吗
curl -s --noproxy 127.0.0.1 http://127.0.0.1:8787/healthz
# 期望：{"ok":true}

# ③ 白板里到底有什么
hermes kanban list | head -20
# 期望：任务列表；注意看 status 列，running 的卡有没有对应的进程

# ④ 调度器在不在干活
hermes kanban diagnostics
# 期望：能看到 last_tick / 可派工 profile

# ⑤ 模型总机通不通
curl -s --noproxy 127.0.0.1 http://127.0.0.1:3425/v1/models | head -c 200
# 期望：一串模型名；不通说明 magpie 挂了，所有 worker 都会失败
```

**读探针的顺序永远是：端口 → 服务 → 数据 → 调度 → 模型。** 从下往上查会浪费很多时间，因为下层挂了上层一定不正常。

## 7. 出问题了，先看哪里

| 现象 | 先看 | 大概率是谁的锅 |
|---|---|---|
| 卡在 `ready` 一直不动 | ④ 探针 + `hermes kanban diagnostics` | 调度器没跑，或 assignee 写了个不存在的 profile |
| 卡在 `running` 超过预算 | `hermes kanban list` 看有没有对应进程 | 进程死了但状态没回滚（僵尸卡），reclaim 一下 |
| 派发了但没反应 | 浏览器 Network 面板看 PATCH 状态码 | 409 = 有未完成父任务；400 = 验收为空被拦 |
| 页面白屏 | 浏览器 Console 第一行红字 | 双 React / 产物没重新构建 / 静态目录指错 |
| 数字对不上 | `/api/plugins/kanban/board` 的原始返回 | 前端缓存（5 秒）或 localStorage 里的"今日"标记 |
| worker 报模型错误 | ⑤ 探针 + `~/.config/magpie/usage.jsonl` | 额度用完 / 组里全挂了 / 密钥过期 |
| 找不到某张卡的执行过程 | `task.metadata.worker_session_id` | 有这个字段 → 能跳会话；没有 → 那一轮没记录（断链） |
| dsh 的活找不到 | `~/.dsh/sessions/` | 卡上没回写 `dsh_session_id`（已知断链 2） |

## 8. 为什么这么设计（以及被否掉的方案）

这一节是给"三个月后的你想改架构"准备的。**每条都附了当时的反对意见**。

**① 为什么不自建看板后端？**
被否方案：自己写一套 FastAPI + 任务表 + 看板。
理由：Hermes 的调度器已经 4000+ 行、跑过 24 个真实任务、有原子认领和失败重试。自建等于重写这些，而且会和 `kanban.db` 形成双状态源——**两份真相必然漂移**。
什么时候该推翻：要接第二个执行器（Claude Code 混跑）、要手机批卡、要多人分权限。

**② 为什么看板要跟原生对齐，而不是随便设计？**
被否方案：工作台自己设计一套列（队列/运行/待收…）。
理由：那样你就得记两套词，而且拖拽时的状态映射一定会在某次改动后错位。
注意区分：**对齐的是"状态模型"（8 个状态、名字、顺序），不是"界面长相"**。界面是你自己的。

**③ 为什么验收是"全屏模式"而不是一个 tab？**
理由：验收一天两三波，做成 tab 会 80% 时间空着；**能空着的 tab 会训练你忽略它**。而模式有开始有结束，"清空了"这个瞬间是唯一的正反馈。

**④ 为什么"不收"必须写理由？**
反对意见：会让人懒得退，直接收了。
接受这个代价。因为那句理由是系统唯一的学习输入；可选的话 90% 会是空的。

**⑤ 为什么不上模型分类器（jev 之类）？**
理由：你现在 24 张卡，分类瓶颈不在机器在你想清楚。用 90% 准确率、还会自信地错的组件，去替代一个 1 秒完成、100% 准确的点击，不划算。
什么时候该上：累计 50 张带人工标签的卡、离线评测 top-1 ≥ 90%。

**⑥ 为什么插件不能嵌入 dashboard 页面？**
理由：那是两套导航、两套主题、两个滚动条缝在一起。要么全是你的，要么全是它的；混着最难看，也最难查。

## 9. 四周学习路径

| 周 | 做什么 | 产出 |
|---|---|---|
| 第 1 周 | 读 §1–§4，把 §6 五个探针跑一遍，故意造一张坏卡看它怎么被拦 | 能独立判断"卡为什么不动" |
| 第 2 周 | 改样式：三列宽度、配色、一处文案。走完 `npm run build` 全流程 | 知道产物在哪、为什么不能手改 |
| 第 3 周 | 加一个只读小视图（比如"今日花费"），只读 `/stats`，不写任何东西 | 知道 REST 怎么调、数据长什么样 |
| 第 4 周 | 加一个后端端点（`/api/workbench/dispatch`），前端调它 | 知道前后端怎么接、错误码怎么处理 |

四周之后，你应该能独立回答："这张卡为什么停在这？"——这就是"全面了解"的实际标准，不是能背出架构图。

## 11. 这份文档怎么维护

**三个地方必须同步改**，否则就会开始互相矛盾：

| 改动类型 | SPEC | ARCHITECTURE-SPINE | 本手册 |
|---|---|---|---|
| 新增/删除能力 | ✅ 必改 | 视情况 | §1/§3 补一站 |
| 改数据流或状态语义 | ✅ | ✅ 必改 | §3/§4 重写对应小节 |
| 改技术栈 | — | ✅ | §4.6 / §5 更新 |
| 改端口、路径、版本 | — | ✅ | §2 / §6 更新 |
| 只是踩了个坑 | — | ✅ 坑清单 | §7 加一行 |
| 推翻某个设计 | ✅ 写清"被否方案" | ✅ | §8 补一条 |

**触发点**：每次提交涉及 `workbench-app/`、`workbench-ui/`、`routing.json`、profile 配置时，回头看一眼本手册有没有过期。**改完不更新，等于给别人（包括三个月后的你）留了个陷阱。**
