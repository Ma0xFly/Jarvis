## v0.1 → v0.2 修订记录
1. **执行不再全给 dsh**：按任务类型分流——长编码 → dsh；搜集资料/做表格/日常杂务 → Hermes profile 自营。dsh 也可以作为 kanban worker 领任务（它有 tool-bash，能直接调 `hermes kanban` CLI 回写状态）。
2. **todo 两层分离**：人看的待办表（输入侧）≠ AI 的任务状态机（调度侧）。输入侧就是 Hermes dashboard 的 Kanban 页 + REST API；不自建 todo 服务。
3. **可视化工作台**：确有必要（远程添加 todo + 监视任务），但**用 Hermes 自带 dashboard，不自建**。可挂本机或 ECS。

## 0. 架构总览（全本地 + 可选远程面板）

```
【输入侧】你                 【大脑】                       【手脚】              【知识】
Hermes dashboard      ┌─────────────────────────┐
(浏览器，本机或ECS) ──→ │  Hermes Agent 管家 profile │──→ worker-A: hermes profile   Obsidian
  /tasks 建任务        │  · kanban = 状态机+消息总线 │    (资料搜集/表格/杂务)      (obsidian-mcp
  拖卡片/看实时状态     │  · cron 定时 / webhook 事件  │    长任务走 magpie strong-lane  只读归档)
                      │  · memory + skills          │
Hermes cron/webhook ──→│  · 「定了的事」决策文件      │──→ worker-B: dsh headless
                      └───────────┬─────────────┘    (长编码/DeepSeek系任务)
                                  │                    经 tool-bash 调 hermes
                                  ▼                    kanban CLI 回写状态
                     magpie gateway (127.0.0.1:3425)   ←—— A2A：kanban.db 就是
                     路由组/配额故障转移/masking/预热        对等通信总线（官方设计）
                                  │
                                  ▼
                     火山方舟 / 硅基流动 / 订阅 / 本地模型
```

**A2A 说明**：Hermes 官方设计里 kanban 就是跨 profile 的对等协作总线（任意 worker 可读写任意任务的 SQLite 行）。dsh 作为 worker 时通过其 tool-bash 执行 `hermes kanban show/comment/complete/block` 完成双向通信；Hermes worker 同理可 `dsh --profile headless "子任务" --json` 调用 dsh。**不需要自建任何 RPC/消息协议。**

**todo 双层语义**：
- **你看的待办表** = dashboard Kanban 页的 triage/todo 列（网页输入，30 秒上手）
- **AI 状态机** = 同一张表的完整生命周期 `triage → todo → ready → running → blocked → review → done`，dashboard 的「拖拽」和「AI 调度」读写同一个 kanban.db，永不漂移

## 2. worker 分派矩阵（核心更新）

| 任务类型 | worker | 模型路径 | 理由 |
|---|---|---|---|
| 长编码/重构/多文件工程 | **dsh headless** | magpie group strong-lane（或 DeepSeek 官方） | dsh 的 harness 强在长任务上下文管理 |
| 搜集资料/调研/查资料 | **Hermes profile** | magpie group（intent routing） | Hermes 有 browser/web_search/Exa 全套工具 |
| 做表格/Excel/PPT | **Hermes profile** | 同上 | 你已有 xlsx/officecli/ppt-master skills，dsh 没有 |
| 运维巡检/服务器检查 | **Hermes profile** | cheap-lane | terminal 工具 + 你已有的排障档案 skills |
| 剧烈重构前的独立 review | **dsh headless**（只读模式） | 强模型 | 跨模型审查（卡兹克：Claude 写 GPT 审），dsh 工具面够用 |
| 信息过滤/打标签/摘要 | **Hermes profile** | cheap-lane | jev 位，v2 换本地 Qwen |

分派落法：`kanban create ... --assignee <profile名>`，assignee 即 worker。建 2-3 个 Hermes profile（researcher/housekeeper/reviewer）+ 1 个 dsh 通道；dsh 的入队方式 = 约定 skill 里写明「assignee 为 coder-dsh 的任务，由管家 profile 代领后 `dsh --profile headless` 执行」或写一个 3 行 systemd timer 轮询领单（二选一，实测后定）。

#### 2d-0 内核边界事实（2026-11-04 逐条核实，决定"要不要碰源码"）

| 要做的功能 | 依赖的现有能力 | 结论 |
|---|---|---|
| 任务详情抽屉 | `GET /plugins/kanban/tasks/{id}` 一次返回 `task / comments / events / attachments / links / link_tasks / child_results / runs`；实测 `t_5e3a7d36` 返回 2 评论 + 12 事件 + 1 run | **零后端改动**，注释原文 "Drawer returns the FULL summary" |
| 显示待拍板问题 | `task.block_kind` + `tasks.result` / `latest_summary` / `block_reason` | 零改动 |
| 回答并续跑 | `POST /tasks/{id}/comments` + `PATCH /tasks/{id} {"status":"ready"}` | 零改动；blocked→ready 由 `_drag_to` 转入 `unblock_task`，是设计好的 re-open 路径 |
| 回执解析（ask/notice/later） | 前端读 `comment.body` / `run.metadata` | 零改动（解析在前端） |
| hops 计数 | 读写 `task.metadata`（`kanban_create` 支持 metadata 之外的字段，hops 可写 comment 或 result） | 零改动 |
| 分派规则路由 | `routing.json` 由我们自己的建卡入口与 worker 读取 | 零改动（与 Hermes 无关） |
| **答后续原会话** | `gateway/session_kanban.py:89` `request_id = kanban:[board,task_id,run_id]` → 一次 attempt 一个会话 | **必须改上游内核，本计划不做**（理由见 2f） |

三个必须记住的坑：
1. **`kanban_block` 只有 `task_id / reason / kind`，没有 metadata 参数** —— 所以"优先读 `metadata.ask`"落不了地。worker 要在 block 前先 `kanban_comment` 写一段 ```ask 代码块（结构化选项），前端读最近一条含该块的评论。
2. **恢复走 `ready` 不走 `todo`**：blocked→todo 会走 `_set_status_direct` 裸写状态，绕过 `unblock_task` 的 block_kind 迁移与事件；ready 才是正规 re-open，且在有未完成 parent 时会自动落 `todo`（并可能返回 409，前端需处理）。
3. **`running` 不能手动设**（`_RUNNING_DIRECT_MSG`），任何"恢复"只能落 todo / ready。

#### 2d-1 待拍板卡片 + 详情抽屉（P0）
- 抽屉内容：标题/正文全文、状态与 `block_kind`、`latest_summary`、最近 20 条评论、run 列表（状态/耗时/费用）、附件、父子链接
- 问题来源（按优先级）：① 最近一条含 ```ask 代码块的评论 → 渲染选项按钮；② `block_reason` / `latest_summary` 文本；③ 纯文本框
- 提交：`POST /tasks/:id/comments` 写 `回答：…` → `PATCH {"status":"ready"}`；409（有未完成 parent）时提示"已转为 todo，等 parent 完成"
- Hermes worker 上下文本来就会带最近 30 条评论，下一轮能读到答案；不追求 autoloop 的“原会话续接”
- 验收：建一张 blocked 卡（带 ask 块）→ 工作台点选 → 下一轮 worker 引用答案并完成
- 注意：`running` 不能手动设；恢复只走 todo / ready

#### 2d-2 回执协议移植（P1）
- worker 完成时在 summary 或 metadata 里放固定 JSON 块：
```json
{
  "ask":   [{"title": "怎么发货？", "text": "两种方式今天都能发。", "options": ["快递", "自提"], "key": "shipping"}],
  "notice": "已完成库存核对，无需操作",
  "later":  {"at": "2026-11-04T18:00:00+08:00", "why": "复查线上版本"}
}
```
- 插件解析：ask → 渲染待拍板卡片；notice → toast/通知；later → 写 scheduled + not_before
- 没有该块 → 按普通纯文本 summary 处理，保持兼容
- 先只覆盖 ask / notice / later，不实现 autoloop 的 events / resolve 全协议
- 验收：worker 输出 ask → 卡片出现在「待拍板」；回答后任务继续

#### 2d-3 定时唤醒（P1）
- `scheduled` 增加 `not_before`（优先放 task metadata，避免改 kanban schema）
- gateway 每 tick 扫 `status=scheduled AND not_before <= now` → unblock 到 todo/ready
- UI 卡片显示「将于 11-04 18:00 唤醒」，支持手动提前唤醒
- 验收：schedule 5 分钟后到点自动回队
- 与 autoloop `later` 的差异：只做任务级唤醒，不做跨会话恢复

#### 2d-4 事件接入（P1）
- `POST /webhooks/github`：验签 → 五字段 `source / type / object / summary / link` → `kanban_create(idempotency_key=<delivery id>)`
- 通用 `POST /webhooks/custom` 同 schema；QQ 以后走 NapCat → 同一入口
- GitHub 轮询兜底：每 5 分钟 `gh api` 查新 issue，稳定 id 去重
- 验收：同一事件重复投递只建一张卡；新 issue 5 分钟内进 triage/todo

#### 2d-6 跳数熔断 + 花费统计（P2）
- **不要用 parent 链长度算层数**：人工拍板的卡（blocked→ready）常无 parent，链断则计数归零，等于没熔断。改为 hop 计数落 `metadata.hops`，建子任务时 `child.hops = parent.hops + 1`，超过 8 层拒绝建卡并 comment
- autoloop 的 TTL 跨"人工问答 / 定时复查"都不清零，这一点要照抄：hops 只随完成清零，不随 unblock 清零
- 花费：从 `~/.config/magpie/usage.jsonl` 按时间窗 + 任务 run 起止聚合，写入 task metadata
- UI：已完成行/任务详情可选显示 token 与费用
- 验收：构造 9 层链 → 第 9 层被拒；单任务能看到估算花费

#### 2d-7 分派规则 JSON（P1，借 autoloop 的真正价值点）

- 目标：迁到 `~/Projects/Jarvis/routing.json`，字段对齐 autoloop 的 `Rule`：`{name, when:{source,types[]}|{cron}, to, cwd?, skills?, priority?, tell}`

#### 2d-8 会话追溯与记录档（2026-11-04 核实）

前提澄清：`assignee` 是**本地 profile 名**（模型 pin + skills + SOUL.md + 记忆），不是 IM bot；worker 会话的 `platform='cli'`，与 telegram/discord 无关。卡片上看不出会话，是 UI 缺位，不是没记录。

**派发链路（v0.22.7 实测）**
```
dispatcher tick(60s) → 扫 ready, ORDER BY priority DESC, created_at ASC
  → 原子 claim（claim_lock + current_run_id）
  → spawn `python -m hermes_cli.kanban_worker_client`
  → 子进程 WS 连本机 gateway，调 kanban.run
  → gateway/session_kanban.py:89
       request_id = "kanban:[board, task_id, run_id]"
       sid = local_identity(profile_id, subject, request_id)
       create_local_session(...)   # source='kanban', platform='cli'
  → 首条 user message = "# Kanban task t_xxx: <标题>"
  → kanban_complete/block → socket 关闭
```
一次 attempt 一条会话，会话 id 由 `(board, task, run)` 哈希派生。

**dsh 是第二层嵌套**
```
coder 的 Hermes worker 会话（local-xxx）
  └─ dsh --profile headless --json "…"
       └─ dsh session-<uuid> → ~/.dsh/sessions/<group>/session-<uuid>/session.v4.jsonl.zstd
          NDJSON → 当前重定向到 /tmp/dsh-<ts>.ndjson（断点）
```

**记录档落点（实测）**

| 位置 | 内容 | 反查 |
|---|---|---|
| `state.db` → `sessions` | 443 条，其中 **kanban 来源 34 条** | `hermes sessions list --source kanban`，workspace 列显示 task id |
| `state.db` → `messages` | 单条 kanban 会话实测 32 条消息 | `hermes sessions export`（JSONL/MD），有 `messages_fts` 全文索引 |
| `task.metadata.worker_session_id` | **Hermes 自动写入**，真实样本 `local-872836e0…` | 卡片可直接跳会话 |
| `kanban/logs/<task>.log` | 完整 transcript（含 reasoning/工具调用），最大 72 KB | 失败时仅 1 KB，**不可作记录档** |
| `task_events` / `task_runs` | 状态迁移 + 每轮 summary/metadata | 完整 |
| `~/.dsh/sessions/` | 18 个 dsh 会话 | **断链**：卡上无 dsh session id |

`config.yaml`：`sessions.auto_prune: false`，`retention_days: 90` 仅对手动 `prune` 生效——记录不会自己消失。

**三处断链与修复项**

| # | 断点 | 修法 | 归属 |
|---|---|---|---|
| 8-1 | 抽屉不显示会话入口 | 读 `task.metadata.worker_session_id` → 打开/导出该会话；数据已在 `GET /tasks/{id}` 返回体里 | workbench 前端，纯 UI |
| 8-2 | dsh session id 未回写 | `dsh-delegation` 验收条款加硬要求：`kanban_complete` 的 metadata 必须带 `dsh_session_id`。**实测 NDJSON 首行即** `{"type":"session","sessionId":"session-<uuid>","cwd":"…"}`，直接解析该行 | `~/.hermes/profiles/coder/skills/dsh-delegation/SKILL.md`，需用户授权后改 |
| 8-3 | NDJSON 落 `/tmp` | 改到 `$HERMES_KANBAN_WORKSPACE/.dsh-runs/<ts>.ndjson`，与任务同寿命。注意 dsh 自身会话按 **cwd 分组**存 `~/.dsh/sessions/<cwd 编码>/session-<uuid>/`，所以必须 `cd <repo>` 再跑，组名才可读 | 同上 |

**范围外**：state.db 备份策略不在本版（用户 2026-11-04 明确不做）。已知风险留档：state.db 约 2.8 GB 且为唯一存储，磁盘/损坏即全部丢失。

**验收**：任取一张已完成卡，抽屉点「打开执行会话」→ 能读到该轮完整对话；跑一次 dsh 任务 → `metadata.dsh_session_id` 存在，且 `dsh --session-id <id>` 能续上。

### Phase 2f · 是否自建看板系统（2026-11-04 评估结论：**暂不立项**）

结论：**不新建看板后端，继续用 workbench-app（前端）+ kanban.db（唯一状态源）**。理由与触发条件留档，避免反复讨论。

| 判断维度 | 结论 | 依据 |
|---|---|---|
| 卡兹克那套有看板吗 | **没有** | 只有 `agent-autoloop status` 一行文本 + 一个游戏化观赏页，观赏页不能下发任务 |
| 差距在哪 | 回执协议 / 事件合并 / 规则校验 / 跳数熔断 | 全部可在现有架构上补（2d 表，合计 ~5 天） |
| 自建要重写什么 | claim/lease、失败熔断、上下文注入、artifact、notify、多 board、权限 | Hermes 现成 `kanban_db_dispatch.py` 2964 行 + `kanban_db.py` 4000+ 行，已跑过 24 个真实任务 |
| "续原会话"能否自建解决 | 不能 | 执行仍走 Hermes gateway session；除非自建后改用 `hermes chat --resume`，代价是放弃 gateway 的并发/权限/artifact/notify |

**只有当以下任一条成立时才推翻本结论、另立项目：**
1. 要接第二个执行器（Claude Code / Codex 与本机 Hermes 混跑）——gateway session 绑死自家 worker，此时薄中台才划算；
2. 要手机批卡（飞书/Telegram 卡片）——Hermes 无好用移动端，这是最可能先触发的一条；
3. 要多人使用（同事提意见、分权限）。
